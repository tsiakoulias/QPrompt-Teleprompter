## Original report claim

- **File:** src/prompter/Prompter.qml:415-416, src/qmlutil.hpp:84-94
- **Severity:** Critical
- **Code:**
  ```cpp
  Q_INVOKABLE void run(const QString &command) {
      QStringList parts = QProcess::splitCommand(command);
      const QString program = parts.takeFirst();
      QProcess::startDetached(program, parts);
  }
  ```
  ```qml
  else if (m.url.startsWith("sys://"))
      qmlutil.run(m.url.slice(6));
  ```
- **Analysis:** The prompter scrolls past markers and checks `m.url`. If URL starts with `sys://`, the rest is passed to `QProcess::startDetached()` with zero sanitization. A crafted `.html` file with `<a href="sys://malicious">` causes arbitrary command execution when the prompter scrolls past it.
- **Impact:** Remote code execution via shared prompter script files. Any document containing `sys://` anchor hrefs achieves arbitrary command execution with user privileges.

## Patch

- **Root cause:** `sys://` markers are a *deliberate* live-production automation feature (sibling
  of `obs://scene/`; the named-marker sheet's "Command to execute" field even advertises
  `sys://cmd arg`). `markerCompare()` (`src/prompter/Prompter.qml`) dispatches a marker as the
  prompter scrolls past it: a `sys://` href is sliced and handed to `qmlutil.run()`
  (`src/qmlutil.hpp:84`), which does `QProcess::splitCommand` → `QProcess::startDetached` with no
  sanitization and no confirmation. Because marker hrefs are **document content**, merely opening and
  prompting an untrusted script (`<a href="sys://…">`) executes arbitrary commands with the user's
  privileges — CWE-78. Real defect confirmed in current code (the report's snippet is slightly stale:
  `run()` already has an `if (parts.isEmpty()) return;` guard, which does nothing for the RCE).
- **Fix:** Least-privilege / safe-by-default, without breaking the intended feature. Gate the
  `sys://` dispatch behind a new persisted, default-**off** setting `systemCommandsEnabled`
  (`else if (systemCommandsEnabled && m.url.startsWith("sys://"))`). Persisted via a `Settings`
  block (category `system`) exactly like the OBS toggle one block above, and opted into through a
  desktop-only `CheckBox` in the marker command sheet. With the flag off, the sole call site of
  `qmlutil.run()` (grep-confirmed: one site) is unreachable from documents; once a user explicitly
  enables it, behavior is byte-for-byte as before, preserving the hands-free, silent-while-scrolling
  automation the feature was designed for. `qmlutil.hpp` left unchanged — the trust boundary is the
  single document→command dispatch in QML.
- **Files changed:** `src/prompter/Prompter.qml` (+9/-1), `src/kirigami_ui/PrompterPage.qml` (+15)
  — the opt-in `CheckBox` uses a `contentItem` with `Text.Wrap` so the label fits the fixed-width
  sheet in any translation instead of eliding.
- **Verification:** Clean Craft build (exit 0); qmlcachegen recompiled `Prompter_qml.cpp` and
  `PrompterPage_qml.cpp` with no errors (compile-time QML type-checking of the new property, Settings
  alias, gated expression, and CheckBox). Headless offscreen launch produced no error referencing
  `systemCommands` / no assignment or ReferenceError from the change; only pre-existing warnings
  (Kirigami OverlaySheet `implicitHeight` loops on every sheet, the separate `Units is not defined`
  bug present because this branch is cut from `main`). Static proof of the gate: `qmlutil.run` has
  exactly one caller, now guarded by a default-false flag, so untrusted documents cannot reach
  `QProcess::startDetached`.
- **Commit / PR:** `7ed63a3` on `fix/gate-system-command-markers` (pushed to origin).
